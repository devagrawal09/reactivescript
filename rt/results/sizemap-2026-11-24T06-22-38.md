# RX production bundle byte map

Generated 2026-11-24T06-22-38. Attribution is the **first** esbuild pass (`metafile: true`, minify on), same compile, defines, and conditions as `rx-bundle.ts`. Group min bytes are `metafile.outputs[*].inputs[file].bytesInOutput`, summed. % is of that pass1 output.

A second esbuild pass (what `rx-bundle.ts` prints) drops what folded arms left unused. That pass has one input, so it cannot be attributed. **pass2 shipped** is that number. pass1 group bytes are an upper bound on the shipped bundle by `pass1−pass2`.

`gz~` is gzip level 9 of the **concatenated input source** of the files in the group that contributed any output bytes (full files, not the tree-shaken slice). It is not a partition of the bundle. **These do not sum**, and they do not sum to the true bundle gzip. The true gzip of the pass1 minified bundle is the `gz~` cell of the pass1 total row. pass2's gzip is the shipped gzip.

base is `rx-store-proto-base`, mode plain, Solid prod (`store-proto-base`). select and manifest are `rx-store-proto-features`, Solid `store-select` (`store-proto-features`). select defines the RX switches on and leaves `__SOLID_STORE_*__` undefined (the select build treats that as on). manifest defines each switch from the compiler manifest. base and features are different Solid checkouts, so base vs select is not a flag delta. sel−man is.

Compiled modules were written under `rt/tmp/`, not into the worktrees.

## What the numbers say

pass1 and pass2 differ by ~300 B on every variant. The second pass is not where the bytes are. A module in the pass1 table is in the shipped bundle. `gz~` is gzip of the full input sources that contributed, not a share of the bundle gzip. Those columns do not sum, and they do not sum to the true gzip (the pass1-total `gz~` cell, and the pass2 row under it).

base vs select is two Solid checkouts, both with every feature on. select is bigger (counter 148,088 vs 139,303), mostly `store: core` (28,286 vs 20,665). sel−man is the flag delta, on the features checkout only.

### What stays even though the program cannot use it

Counter's compiled program calls `__rt.owner`, `source`, `untrack`, `reg`, `hacc`, `snapshot`, `show`, `B`, plus the DOM helpers the JSX compiler emits (`template`, `insert`, `delegateEvents`, `runHydrationEvents`). It does not call a store, a probe, a boundary, or `hydrate`. The runtime still ships them, because `createApp` returns one object and the unused methods are still properties of it, and because `mount` mentions `hydrate`.

**Store engine, stores=false.** `signals/store/store.js` is 14,234 B. Chain: `store.js` ← `./store/store.js` re-export of `isStoreTarget` / `storeGet` / `storeSet` / `storeKeys` / `storeProxy` in `signals/index.js` ← `@solidjs/signals` in `rt/store-ops.ts` ← `./store-ops.ts` in `rt/rt-web.ts` ← entry. `store-ops.ts` imports those names. `rt-web.ts` does `import * as S` and calls `S.out` / `S.isT` / `S.raw` from `fmt`, `show`, and `eq`, which the counter does use. The `__RX_STORES__` guards fold the calls (`store-ops.ts` itself is only 351 B), but the imported module is still live: pass2 drops 342 B from the whole bundle, not 14 KB. `foldTarget`, `traps`, and `proxyOf` are in the identifier-kept output. `store/utils.js` (omit/merge, 6,313 B) does not move with the flag. It is the `omit` property on the app object and `web.js`'s `import { omit }`. `store/affects.js` (1,552 B) is `./store/affects.js` in `affects.js`, and `affects` is a method on the app object. The header says a program that never marks a store carries none of it. The method reference keeps it.

**Probes and lanes, no `pending?` and no `guess`.** `verdict.js` is 6,271 B, `lanes.js` 7,230 B, `truth.js` 559 B, `guesses.js` 1,982 B. `rt-web.ts` imports `isPending` and `latest` from `solid-js` and puts both on the app object (`isPending: f => isPending(...)`). `index.js` re-exports them from `./core/verdict.js`. `verdict.js` has a real named import of `lanes.js` (`screenOf`, `keptGuess`, `ahead`, `verdictLane`, `isVerdict`, `waiting`, `heldMountUnder`). That is the pull. `core.js` also has a bare `import "./lanes.js"`, and `signals.js` a bare `import "./core/verdict.js"`. esbuild warns those are ignored (`sideEffects: false`), so they are not the pull. `guesses.js` is `import { optimisticWrite } from "./core/guesses.js"` in `signals.js`. The optimistic flag does not remove it (sel−man is 7 B on counter, 0 on rows and keyed). Same 1,982 B with optimistic off.

**Boundaries, deferred, affects, no `<Loading>`.** `boundaries.js` 4,713 B is `createErrorBoundary`, used by `catchAcc` (`catchMemo` on the app object) and by `TypedErrored`. `deferred.js` 1,107 B is the `deferred` method. `affects.js` 705 B + `affects-marks.js` 663 B are the `affects` method; deferred also imports the mark core. Counter calls none of these. They are properties of the object `createApp` returns.

**Hydration, never hydrated.** The JSX compiler always lowers DOM with `hydratable: true` (`compile/jsx.ts`), so `main.mjs` imports `runHydrationEvents` and calls it. `mount` is `hydrating ? hydrate(...) : render(...)`, and entry calls `app.mount(main(app))`. esbuild does not drop the other arm. `hydrate` calls `enableHydration`, which assigns `hydrateStoreLike`. In the identifier-kept counter bundle: `hydrate` 2,757, `enableHydration` 1,425, `hydratedCreateLoadingBoundary` 2,463, `hydrateStoreFromAsyncIterable` 1,780, `hydrateStoreLikeFn` 1,476, `portalImpl` 1,223, `runHydrationEvents` 1,176, `installHydrationRuntime` 862, `createShadowDraft` 715. **Always-on harness.** `entry.mjs` always imports `api.mjs` (430 B) even when the program has no `./api` import. `primsSolid` is 131 B because `prim` is a method on the app object. `features.ts` is 87 B (the switch module, imported for its side effect).
