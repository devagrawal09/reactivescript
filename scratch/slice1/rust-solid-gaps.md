# Rust-solid: slice 1 gaps

## Direct relevance

- **2-compute-effect_cleanup, 3-compute-effect_cleanup**: STATUS.md:35-36 calls these same-tick and overlapping “action speculation / optimistic visibility.” The first reduced case is an action holding t=30 across gate-b, then writing t=40 (repros/reduced-2-compute-effect_cleanup.json). In the like-button trace, observers must see the guess while save is pending, and see base restored after swallowed failure. Rust has partial plain-signal optimism/base restoration, but no complete speculative visibility transition (DESIGN.md:25). Solid’s createOptimistic overlay gives optimistic reads while preserving base; transaction close clears/reconciles the overlay. These are the two directly path-relevant buckets.
- Flush/commit ordering is implicated in both: STATUS.md:14 says action-family comparison is 0/667; STATUS.md:35-50 labels are first-difference buckets, not proven independent causes. Rust stages writes until flush and commits ordinary intent only when all action bodies finish (DESIGN.md:15,25). Solid actions apply their held writes at action/transaction boundaries and schedule reactive work in Solid’s queue; don’t equate Rust explicit flush with a Solid commit.
- **Indirect/conditional**: 0-compute-compute is dynamic dependency-height/compute ordering; 5-* buckets and oracle timeout/error concern lazy pull/refresh/dormant-node behavior (STATUS.md:37-48). They touch the path only if like-button observers are lazy or refresh is introduced. 1-compute-read is async failure recovery/downstream recompute (STATUS.md:38), relevant to rejection rollback observation but not specifically one-yield commit.
- Remaining non-bucket limitation: action speculative computation and optimistic lanes incomplete; action traces fail (DESIGN.md:25; STATUS.md:14,25). Public action closure may catch rejection, but JSON driver only covers uncaught rejection (DESIGN.md:23; OP-LANGUAGE.md:20). Thus swallowed failure/rollback path is not driven by current JSON action op.

## API/driver shape

Runtime<T> graph; homogeneous T: Clone+PartialEq; Signal<T> weak handle (DESIGN.md:11). Signals stage set/write until flush, optional custom equality, optimistic plain signals with base restoration (STATUS.md:20-25). Memos can be eager/lazy, track dependencies, use refresh and flight-backed pending/latest/loading; effects split compute/apply and have render/user order, prior-applied values and cleanup (DESIGN.md:13-17). Actions are coroutine-style ActionBody returning Yield(flight), Done, Fail; settle/ drain drive continuations; multi-yield and user-side catch possible, but not general Future (DESIGN.md:21-25). Flights are controlled one-shot IDs settled with Ok(value)/Err(error), newer flight supersedes old; drain to quiescence (DESIGN.md:21).

JSON: one array of ops per stdin line, one log array per output line. Ops signal/memo/effect/write/read/latest/pending/flush/owner/cleanup/dispose/refresh/action/resolve/reject; expression forms read/add/mod/choose/untrack/fail/prev/literal (OP-LANGUAGE.md:3-29). Action slices contain writes and optional flight; nonfinal slices yield, final slice ends. No catch syntax (OP-LANGUAGE.md:20).

Structural mismatch: Rust stores committed/last plus revisions and an optimistic base, but exposes no distinct Solid-style pending vs committed view; its optimism is a plain-signal restoration mechanism, not full lane/transaction semantics (DESIGN.md:13,25). No renderer or RX integration (DESIGN.md:5).
